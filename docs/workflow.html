Section 00Orientation

The module aligns the ITS2 by attaching one small linear neural network to every sensor and training all of them simultaneously against a track-fit residual. It is a track-based alignment expressed as a learning problem rather than as a single large linear system.

Each of the 24 120 ALPIDE chips owns a YSensorCorrection object: a two-input, three-output linear network with no hidden layer. It maps the measured cluster position in the sensor frame, (s1, s2), to a correction (cs1, cs2, cs3). The corrected hits of a multi-prong event are fitted with a circle in the bending plane and a straight line in the z–β plane; the sum of normalized squared residuals is the cost. Gradients propagate back to the per-sensor weights, and an analytic Jacobian re-expresses those weights as six rigid-body alignment parameters — three rotations and three translations per sensor.

24 120independent sensor networks
11network parameters per sensor
6rigid-body DoF per sensor
50 000source entries read per step
≥ 6tracks required per event

Three nested repetition scales matter and are easy to confuse. An epoch is one pass over the training events inside a single job. A step is one complete job: five epochs, its own weight files, its own residual monitoring, its own archive. A campaign is a sequence of steps driven by process_all_train.sh Tag stepI stepF, in which each step is seeded from the previous step's weights. Convergence is expected across steps, not within one.

YDetectorGeometry is a process-wide singleton reached through the yGEOM macro. Its constructor loads the geometry, applies the starting alignment, instantiates o2::its::GeometryTGeo and fills the T2L, T2GRot and L2G matrix caches. Every coordinate transform in the module — GToS, SToG, LToG, GToL — goes through it, so the starting alignment is baked into the geometry rather than carried as an explicit offset.

The sensor frame

The module works in a sensor-local frame (s1, s2, s3) that differs from the O2 local frame and differs again between barrels. For inner-barrel chips (s1, s2, s3) = (−l3, −l1, l2) with l1 the row direction, l3 the column direction and l2 the sensor normal. Outer-barrel chips additionally flip sign according to their position within the module, which the code tracks through the per-sensor mounting direction fmntdir = ±1. In this frame s1 and s2 span the sensor plane and s3 is the normal, so a correction along s3 is a displacement out of the plane.

Section 03Beam-profile pass

run_profile_beam.C runs once per campaign, before the first step. It projects the reconstructed primary vertices into three z slices of half-width 1.5 cm, centered at z = −7.5, 0, +7.5 cm, fits a Gaussian to the x and y projection of each slice, and fits a first-order polynomial to the three resulting means. The four coefficients are written as preprocessor defines into YMLPBeamProfile.h, which is included by YMultiLayerPerceptron.cxx at compile time.

How the beam constraint is supplied

There are two routes to the beam point, and both read from a file rather than assuming a nominal axis. The per-event route, which is the one active in the cost, takes the beam center straight out of the input tree: GetCost_Beam_CircleFit reads the event vertex (X1, X2, X3) through the addition branches and builds BeamCenter(BeamPos[0], BeamPos[1], BeamPos[2]). The parameterized route uses the coefficients this pass writes into YMLPBeamProfile.h, evaluating BeamCenter(XZ1·z + XZ0, YZ1·z + YZ0, z) at the event's z; that line is present in the source and selected by swapping which BeamCenter is constructed.

The per-event vertex is the more precise constraint when the sample provides a reliable one, which is why it is the default. The fitted profile remains the fallback for samples where the per-event vertex is unusable, and its slope is in any case a direct diagnostic of the beam-line quality — the values in the committed header correspond to a beam-line tilt of about 0.3 mrad in x and 0.7 mrad in y.

Section 04Data preparation

YAlignment::PrepareData(nDATA, jparallel) converts the reconstruction output into the flat training tree the network reads, and at the same time assembles the textual description of the network topology.

Topology string

The layout handed to YMultiLayerPerceptron is assembled from three groups: inputs s1[0..6], s2[0..6] — fourteen sensor-plane coordinates; outputs Stave[l], Chip[l], ChipID[l] for seven layers — twenty-one addressing branches that route each hit to its sensor network; and an addition group X1, X2, X3, P1, P2, P3, evno, ntracks carrying the event-level quantities. The output group is addressing, not regression targets: the quantity being minimized is the track fit, not a labelled truth.

Selection and normalization

  • Events with fewer than nTrackMax = 6 tracks are skipped — the cost is defined on a multi-prong event sharing one vertex.
  • Events with more than one associated vertex in the time frame (nvtx > 1) are skipped, to avoid pile-up contaminating the vertex constraint.
  • For every one of the 24 120 sensors the active-area corners are transformed (row, col) = (0,0) and (511, 1023) through LToG then GToS, giving per-sensor minima, maxima and spans in s1 and s2. These define the input normalization; the network sees coordinates shifted to [−0.5, +0.5] via fNorm_shift = 0.5.
  • An event-weight hook (GetEventWeight, based on the z acceptance of each layer) exists but the cut on it is commented out in the current version.

The result is MLPTrain/XXXXtrain/XXXXtrain.root containing InputTree. The training and test samples are then carved out of it by event number: evno % 10 ∈ [0, 6) is the training set and [6, 8) is the test set used inside the job. The remaining 20 % is attached to neither TEventList and is held in reserve — it never enters the loss, the line search or the early-stop logic.

Two levels of validation

The evno % 10 split is the in-job control on a single prepared sample: it is what the loss curve compares, and it is what detects a step over-fitting to the subset of sensors that happen to be well populated in that sample. It is deliberately small, since every event withheld is one not contributing to a 24 120-sensor gradient.

Genuine validation is done separately, on an independently prepared sample that the campaign has never seen — a different run or fill, reconstructed and converted through the same upstream chain into its own XXXXinput.root. That pool is evaluated by running a job with nEPOCH = 0 against the trained weight set, which performs the epoch −1 pass only and produces the full residual and monitoring output without updating anything. Judging an alignment on the in-job test slice alone would be judging it on the same detector conditions it was fitted under.

Section 05Network topology

There is no deep network anywhere in this module. The model is 24 120 copies of a single affine map, plus a hierarchy of shared units that is built but currently not trained.

The detector-unit hierarchy

Alongside the flat sensor collection, BuildDetectorUnitNetwork constructs an eight-level tree of YSensorCorrection objects that share parameters across increasingly fine groupings:

LevelGroupingMultiplicity
0whole detector1
1barrel group — IB, OB1, OB23
2half-stave index1 or 2 per group
3chip position along z within a stave9 … 98
4layer within the group2 or 3
5half-barrel2
6stave index within a half-barrel6 … 24
7half-stave within the stave1 or 2

This is the natural home for a coarse-to-fine alignment: releasing level 1 first fixes the three barrel groups as rigid bodies, then progressively finer levels absorb the remaining structure. The tree is built, its update states are initialized, and its weights are dumped every epoch into weightsDU*.txt.

Active configuration

In the present version the hierarchy is inert. Every SetUpdateState(true) call in SetDetectorUnitNetworkUpdateStateUser is commented out, and the learning method selected in run_train_circle.C is kStochastic, which updates the per-sensor networks directly rather than through the hierarchy. The hierarchical path (kBatchDetectorUnitUser, ComputeDCDwDetectorUnit, MLP_BatchDetectorUnit) is complete but not exercised. The weightsDU files are consequently written and re-read as identity carriers.

Section 06The cost function

This is the physics of the module. A cost is defined per track, summed over the tracks of an event, normalized by the event's degrees of freedom, and summed over events. The per-track chain runs in GetCost_Beam_CircleFit.

From track cost to event cost

GetCost_Beam sums the track costs of an event and divides by ndf = (2(nlayer + 1) − 4) × nused + 1 = 12 nused + 1, where nused is the number of tracks that survived. Two coordinates per hit across seven layers plus the vertex point give sixteen constraints; four helix parameters are fitted; the extra unit accounts for the shared vertex. If every track of an event is rejected the event itself is counted as lost and contributes zero.

The charge-symmetry term

A second contribution is added at the epoch level rather than per track. For each of twenty azimuthal patches the module accumulates Σ q · pT over the tracks falling in that patch. A residual net charge–momentum asymmetry in a φ sector is the signature of a curvature bias — a sagitta-like weak mode that leaves the track χ² almost untouched while systematically distorting the momentum scale. The absolute value of the sum, normalized by the number of training tracks, is added to the reported loss, and the positive and negative track counts per patch are printed each epoch so that the asymmetry can be watched directly.

Section 07The optimization loop

YMultiLayerPerceptron::Train(nEpoch, "graph, text, update=1") holds the loop. Its structure is four nested scales, and each boundary is where something is written to disk.

Epoch −1: the baseline

Before the first update the module performs a full evaluation pass labelled epoch −1. It calls PrepareDumpResiduals and ComputeTrackProfile, evaluates the training and test costs, and writes Residual_Epoch_At_-1.root, NTracksBySensor, and the sensor and half-stave track-occupancy plots. This baseline is what every later epoch is compared against, and it is also the pass that populates the update-sensor list. Setting nEPOCH = 0 makes the job stop after it — the standard way to produce monitoring for an existing weight set without training.

Update-sensor list

UpdateSensorsList.txt carries one line per ChipID with the number of tracks seen and a status flag. Its behavior is set at compile time by MONITORONLYUPDATES_MODE:

ModeBehavior
−1Flexible — the list is regenerated from the occupancy at every epoch.
0Generate — the list is produced from the epoch −1 pass and the job returns without training.
1Fixed (current) — the list is loaded from the previous step and re-emitted unchanged, so the set of sensors under correction is stable across a campaign.

The occupancy threshold Min_Cluster_by_Sensor is 0 in the committed configuration, so no sensor is excluded on statistics alone; the list is inherited rather than recomputed.

Learning rate and schedule

The nominal learning rate is built from a target resolution rather than tuned as an abstract number: η = UpdateConstant × UpdateScale × (DETRES × 10−4)² with 0.05, 10−7 and DETRES = 1000 µm, giving η = 5 × 10−11 in the squared-centimeter units of the cost. YAlignment::TrainMLP additionally sets τ = 100 e−0.1 s, annealing the line-search bracket expansion factor across the campaign; τ is consumed only by the line search of kSteepestDescent and is therefore inactive under the stochastic method selected in the current version.

Section 08Weights to alignment parameters

CalculateSCWeights is where the module stops being a neural network and becomes an alignment. It runs per sensor, inside the weight update, and performs three operations in sequence.

  1. Assemble the geometric context. The sensor's local-to-global matrix is decomposed into a rotation Rgeom and a translation Tgeom. Two constant matrices, a signed permutation P carrying the mounting direction and an axis-order matrix O, map between the O2 local frame and the sensor frame used here. A diagonal matrix D1 = diag(1/d1, 1/d2, 1) with d1 = 2.991253 cm and d2 = 1.373568 cm undoes the input normalization, and a small offset D2 absorbs the sensor-frame origin shift.
  2. Differentiate the rigid-body map analytically. For each of α, β, γ the derivative of the rotation matrix is written out in closed form and conjugated into the network's parameter space, giving ∂wij/∂α and ∂bi/∂α and their counterparts. The translation derivatives are simply the columns of RgeomPO transposed. Contracting these with the accumulated ∂C/∂w yields ∂C/∂α through ∂C/∂T3 exactly, with no finite differences anywhere.
  3. Update and write back. The six geometric parameters are advanced along their own gradients, each scaled by its entry in the gate vectors Update_aR[3] and Update_aT[3]. Setting an entry to zero holds that degree of freedom fixed for the run without changing anything else, which is the mechanism behind a staged schedule — translations first, rotations released later, or a subset pinned while a weak mode is investigated. The network weights are then recomputed from the updated geometry so that the two descriptions never drift apart. Both are stored: each line of weights.txt is ChipID, five neuron offsets, six synapse weights, aR[0..2] and aT[0..2] — eighteen columns.
Why this matters

Because the mapping is exact and bidirectional, the learned object is a rigid-body alignment by construction and not merely something that resembles one. A per-sensor affine correction left unconstrained would have nine free parameters and could absorb shear and scale that no physical mounting can produce; here it has exactly the six of a rigid body. The network is the numerical vehicle, the geometry is the model.

NetworkParameters/weights.txt in the repository is the deployed parameter set; weights_np.txt is the same file reduced by howto.txt to its first twelve columns, that is, the network description without the geometric one.

Offline analysis

monitor/analysis.sh launches five ROOT jobs in parallel against Residual_Monitor_Epoch_At_-1.root:

  • CheckQuality — curvature against charge and pT in two dimensions and per φ patch, the total χ² distribution, and the charge-symmetry monitor.
  • ImpactParams — impact-parameter and vertex distributions.
  • Residual — residuals by layer, repeated at pT thresholds of 0, 0.3, 0.5, 1.0 and 2.0 GeV/c, since a residual that only closes at high pT indicates a scattering-dominated rather than geometric effect.
  • Residual2D and Profile — two-dimensional residual maps and their profiles.

Separately, YAlignment::ReconstructGeometries(res_level) samples each sensor's active area on a 2res_level × 2res_level+1 grid and writes three geometries — ideal, target and corrected — into Geom/XXXXGeom.root as TNtuples indexed by the full addressing chain. This is the direct route to a sensor-by-sensor displacement map.

Section 10Step chaining

A campaign converges across steps. Three files carry state forward; everything else is regenerated.

Step 0 is the exception: fPrevWeights is empty, so the networks are randomized by Init_Randomize and its sensor-level counterparts, and no update-sensor list is inherited. From step 1 onward the three files above are loaded before the epoch −1 baseline is evaluated, which is why that baseline is directly comparable to the previous step's final epoch.

Learning method

run_train_circle.C selects kStochastic. Of the eight methods declared, three are implemented in this version — kStochastic, kBatch and kSteepestDescent with a line search — plus the two specialized paths kBatchDetectorUnitUser and kOffsetTuneByMean. The conjugate-gradient and BFGS branches are declared with empty bodies and must not be selected.

Offset and slope tuning

kOffsetTuneByMean is a separate refinement pass that shifts each sensor by the mean of its own residual profile rather than by a gradient. It reads seventeen coefficients per chip from OffsetSlopeCorrectionParams.txt. In process_all_train.sh it appears as a commented-out block that would run MLPTrain_Step200/control_all.sh before the campaign; the corresponding directory is not part of the repository, and the pass additionally requires MONITORSENSORUNITprofile to be defined.

Section 12Notes for alignment groups

For readers who align other trackers: this section places the method against the two families most groups already use, and states plainly which parts are conventional and which are not.

What is conventional

  • The objective is a track-fit χ² with residuals in the sensor plane, normalized by a resolution model that adds intrinsic and multiple-scattering terms in quadrature, with the scattering term scaling as 1/(BR).
  • The alignable object is a rigid body with six degrees of freedom per sensor.
  • A vertex constraint from multi-prong events supplies the information that a track fit alone cannot: without it, coherent radial and longitudinal modes are unconstrained.
  • Outliers are removed by hard cuts on the normalized residual and on the total track χ².

What differs from a Millepede-style global fit

  • No global matrix. Alignment parameters are never assembled into a single linear system. The gradient with respect to each sensor's parameters is accumulated independently and applied immediately, so the memory footprint is O(Nsensor) rather than O((6Nsensor)²). For 24 120 sensors that is the difference between a few megabytes and a dense matrix of order 1010 elements. The price is that inter-sensor correlations are not solved in one shot; they are recovered by iterating steps.
  • Iteration replaces inversion. Convergence is empirical and is monitored through the loss curve and the residual distributions, not certified by a covariance matrix. The module produces no parameter uncertainties; a Millepede solution does.
  • Weak modes are attacked by penalty rather than by constraint equations. The charge–momentum asymmetry term per φ sector penalizes a sagitta-like distortion directly in the cost. There is no explicit set of linear constraints fixing the global frame; the reference-sensor mechanism (SetSplitReferenceSensor) exists but is disabled, and the global frame is instead held by the vertex constraint and, where a campaign calls for it, by gating individual degrees of freedom through Update_aR and Update_aT.
  • Robustness by rejection rather than by down-weighting. There is no M-estimator; a track either enters the cost in full or not at all. This is simple and fast but discards information at the edges of the residual distribution.

What differs from a local iterative alignment

A local method aligns one sensor at a time against tracks fitted from the others, and must be iterated to propagate information. Here all 24 120 sensors are updated in the same pass from the same track fits, so information propagates across the detector within a single epoch. The construction is closer to a simultaneous gradient descent on the full parameter vector than to a sequence of local solves — the network formalism is what makes the bookkeeping of that gradient tractable.

Transferable pieces

  • The analytic weight-to-geometry Jacobian is the reusable core. Any alignment expressed as a per-sensor affine map can be constrained to rigid-body motion the same way, with the same guarantee that the fitted object stays physical.
  • The charge–momentum symmetry penalty is detector-independent and cheap: it needs only the track charge, its pT and its azimuth.
  • The learning-rate backtracking guard — revert, divide the step by √10, retry, abandon after four attempts — is a compact substitute for a full line search when the cost evaluation is expensive.
  • The step archive convention, in which each iteration is a self-contained tarball with its own weights, residuals and gradients, makes a campaign auditable after the fact rather than only while it runs.

Honest limitations of the present version

  • The detector-unit hierarchy that would enable a coarse-to-fine schedule is built but not enabled.
  • No parameter uncertainties or correlations are produced.
  • Configuration lives in preprocessor defines, so a scan over cut values requires recompilation and cannot be varied within a campaign.
