ALICE ITS2 ML Alignment

Run Console

Configure, check, compose and launch one alignment run — from a terminal or from a ROOT window, with no Python anywhere. Built for CentOS 7 with ROOT present, which is the only environment it has to work in.

01Why it is shell

The console was originally tools/run_console.py, which served a web UI. It could not run on the machine it was written for: it needs Python 3.8 — shutil.copytree(dirs_exist_ok=) at three sites, ThreadingHTTPServer, f-strings throughout — and CentOS 7 ships 2.7.5. EPEL's python36 is still short of it.

The target has ROOT, and that changes what the console needs. Reading the input tree was the one job that genuinely required a library; root -l -b -q does it, so the uproot dependency disappears and with it the last reason for Python to be involved. The rest — copying a tree, linking large inputs, unpacking a seed archive, patching #defines, launching and tailing — is what shell is for.

Note this is about the console, not the module. The module's own requirements depend on the geometry backend, and by default it still reads through O2 — see section 05.

The layout follows ALICE-ITS2-ML-Alignment-Manager, so both trees are operated the same way: one bash-sourced configuration, one library, one dispatcher, one ROOT window.

02Quick start

eval `alienv load -w $O2_DIR/sw O2/latest`   # only if this tree needs O2

./config/runctl.sh ui         # set everything in one window
./config/runctl.sh doctor     # check this machine has what the run needs
./config/runctl.sh compose    # build the job directory
./config/runctl.sh run        # launch it, detached
./config/runctl.sh log -f     # watch

Exit status is 0 on success and non-zero when a check fails, so these compose into a batch script without parsing their output.

03The window

runctl.sh ui opens a ROOT GUI with six tabs — Inputs, Module, Job, Learning, Selection, Run — an action bar and a log pane. Path fields have a Browse… button: files use ROOT's file dialog, directories use the same TBrowser-style tree the Manager uses. Everything is ROOT's own toolkit, so CentOS 7 needs no extra packages.

The rule that keeps the two halves honest

The window never writes the configuration file, never composes and never launches anything itself. Every button shells out to runctl.sh, so the file format, the validation rules and the job layout live in one place and the GUI cannot drift away from the command line. Whatever the window can do, you can do over ssh with no display.

04What compose builds

compose creates OUTPUT_DIR/JOB_TAG and fills it with:

  • a copy of Ymlp/, monitor/, geometry/, NetworkParameters/, tools/ and the top-level macros
  • symlinks, not copies, for the three large inputs — the data file alone is about 800 MB, and copying it per job would fill the disk for nothing
  • the seed archive unpacked into MLPTrain_Step<FIRST_STEP-1>/, where run_train_circle.C looks for SetPrevUSL and SetPrevWeight
  • a regenerated YMLPParallel.h (it is exactly four defines), an in-place patch of fourteen #defines in that job's DetectorConstant.h, the four eta and clip globals in its YMultiLayerPerceptron.cxx, and the learning method and tree name in its run_train_circle.C
  • run_steps.sh, the generated step loop
The property worth preserving

The module checkout is only ever read. That is what lets the console drive a tree meant to stay untouched — and it is what makes a composed job reproducible, since every knob it ran with is recorded in its own files rather than in a checkout that has since moved on.

05Geometry backend

GEOM_BACKEND picks how the job reads the detector geometry.

ValueReads geometry viaO2 at run time
o2 (default)o2::its::GeometryTGeo, as the module always hasyes
cachea per-chip file built once by tools/export_geometry_cache.Cno

It is a compile guard, YGEOM_USE_O2, written into the job's own copy of Ymlp/inc/YDetectorGeometry.h at compose time — so the two modes are one tree built two ways, and the module checkout is still only ever read. Composing again switches cleanly in either direction.

o2 is the default and the reference. cache exists for machines where O2 cannot be installed. doctor checks what the selected mode actually needs: O2_ROOT for o2, the cache file for cache.

This is also how the cache gets validated

Because the two differ only by that guard, running one configuration under each and comparing the outputs is a direct O2-versus-cache check on identical inputs. That comparison has not been run yet — the cache's alignment-delta convention remains unvalidated, and this is the way to settle it.

06Steps

FIRST_STEP and N_STEPS set a range. Step N reads MLPTrain_Step<N-1>/ and writes MLPTrain_Step<N>/, so the chain continues on its own and only the first step needs the seed archive. Compose writes run_steps.sh into the job directory and run launches it with setsid; it rewrites batch_train per step, files train.log into the step directory and tars the result — the same shape as process_all_train.sh.

If a step fails the run stops there rather than feeding a broken step into the next. status reads run.step, so it can answer “step 3 of 10” even after the window has been closed and reopened.

07The learning rate

eta is not a #define. YMultiLayerPerceptron.cxx computes it in the constructor from three plain file-scope globals: 

double UpdateConstant  = 0.05;
double UpdateScale     = 1.0e-7;
double DETRES          = 1000.0;   // um

fEta = UpdateConstant * UpdateScale * pow(DETRES*1e-4, 2);   // = 5e-11

So the console patches that source file in the job copy, not a header. Nothing is rebuilt for it: run_train_circle.C includes YAlignment.cxx directly, so cling reinterprets the source on every run. The commented-out duplicates a few lines below are left alone, because the patch anchors at the start of the line.

The three constants are exposed rather than eta itself, and the window shows what they come to. Deriving UpdateConstant backwards from a typed eta would silently disagree with the module's own arithmetic, and DETRES is a physically meaningful number — the assumed detector resolution in µm — worth setting on its own terms.

This is the starting value, not the running one

The module backtracks on its own. If the cost rises above training_Epast × 1.005 or Init_training_E × 1.02, it reloads the previous epoch's weights and divides eta by √10, up to four times. The eta in the log will differ from the configured one whenever that has happened — that is the module working, not the setting being ignored.

JOB_VALID_WINDOW sits beside it and does a related job: it clamps how much a single hit's residual may contribute to the weight update. eta scales the step; ValidWindow bounds what any one hit can push.

08Selection

Two pairs of chi thresholds, deliberately different. JOB_CHI_IB / JOB_CHI_OB decide which hits spoil the cost; JOB_CHI_IB_TRAIN / JOB_CHI_OB_TRAIN which hits spoil the weight update. validate refuses a training threshold looser than its cost counterpart, since that would let the update accept hits the cost has already rejected.

Impact-parameter range, and the layer-0 defect

JOB_IP_RANGE_R and JOB_IP_RANGE_Z are the impact-parameter acceptance. In this tree they also decide how much a known defect costs: when a track has no layer-0 hit, its reference point is read from stack memory that was never written, so the impact parameter is meaningless and the track lands far outside the range. It is then dropped from both the cost and the weight update.

Measured on run 539884: 51.6 % of tracks have no layer-0 hit, and 90.85 % of those are marked untrained — 47.33 % of the whole sample. Widening these two values is the only lever available here, short of patching the module. The defect is fixed in the 2025 tree, which projects to the vertex and searches for the innermost layer that actually has a hit.

09What doctor checks

These are the things that cost time to discover late:

  • the input tree exists and holds at least JOB_NDATA entries
  • the seed archive carries weightsDU.txt; without it the detector-unit normalisations stay uninitialised and the cost comes out -nan after a full run
  • FIRST_STEP ≥ 1; at step 0 the module hands LoadUpdateSensorList an empty name and errors out
  • the geometry cache exists when the module is the cache-backed kind
  • free disk, and free memory against the roughly 8 GB a job holds resident — two jobs at once have OOM-killed each other
  • whether this module tree needs O2 at runtime, read from its own sources rather than assumed

It also prints the expected wall clock, from a model fitted on completed runs of this module: 4.8 + 0.00337·nDATA + nEPOCH·0.01431·nDATA minutes, with the evaluation term at 75 % when nEPOCH is 0 because Train() returns before the test pass. Multiplied by N_STEPS.

10Driving another module version

Set MODULE_DIR to any alignment checkout. The console reads that tree's own YMLPParallel.h, DetectorConstant.h and YDetectorGeometry rather than assuming this one's, so it reports that tree's knob values and whether it needs O2. Version independence is by discovery, not by a table.
