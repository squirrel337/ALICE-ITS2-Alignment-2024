Section 00Verdict

A platform is feasible at every tier examined. The obstacle is not data access, not volume, and not the ROOT format — it is that the module's configuration lives in preprocessor defines, which only matters if the interface is meant to launch runs rather than inspect them.

Three things make this easier than it looks. The parameter outputs are plain whitespace-delimited text, small enough to ship whole to a browser. The per-track monitoring tree is a plain POD struct rather than a ROOT class, so it is readable in pure Python. And the visualization vocabulary already exists in the trending macros — roughly 790 lines of ROOT plotting that a dashboard would be porting, not inventing.

Correction to an earlier assessment

My first read of this flagged the Residual_Monitor_*.root tree as needing a ROOT-side exporter because it holds a custom class. That was wrong. YResidualMonitor is declared in YMultiLayerPerceptron.h as a plain struct — no ClassDef, no TObject inheritance, no std::vector members. Its fields are scalars and fixed-size arrays of length nLAYER + 1 = 8, which ROOT splits into flat sub-branches that uproot reads directly. This removes the ROOT dependency from what would have been the most valuable data source, and it changes the recommended architecture.

Browser payload

A detector map needs ChipID plus six alignment parameters per sensor. As Float32 that is 24 120 × 6 × 4 B = 579 KB, plus a one-time geometry table of the same order. Both are static assets. Rendering 24 120 instanced quads is unremarkable for WebGL, and even a 2D unrolled φ–z view is well within Canvas territory. Volume is not a constraint anywhere in this problem.

Occupancy, from the committed set

49 551 936 tracks total, up to 148 294 on a single sensor, and no sensor with zero occupancy — every one of the 24 120 carries status = 1. A map would therefore be fully populated rather than sparse, which is the favorable case for a color-encoded view.

Section 02What is readable without ROOT

This is the question that decides the architecture, so it is worth being precise about.

Formats that are already machine-readable

Two of these deserve mention because they are richer than their file extension suggests.

  • CostGradient_Epoch_At_<e>.txt emits, per sensor and per epoch: Epoch<N> Layer<L> Chip<C> <nhits> hits Grad … AlignPar(R,T) … — the network gradient and the six alignment-parameter gradients together. Per-sensor convergence trending needs nothing but this file series.
  • train_done.log carries fixed-form lines: (Ave)Epoch: <n> learn=… test=… fTotN(E) … fLoss(E) …, COSTMONITOR[TRAINING] EPOCH<n> Fit + CHSYM = a + b = c, and one PSTV#<n> (+) … (-) … |DIFF| … line per φ patch. The loss curve, the fit/charge-symmetry decomposition and the weak-mode monitor are all recoverable by regular expression.

Section 03What the interface should show

For a small internal group that runs the alignment, the value is not in prettier versions of plots that already exist. It is in the questions that are currently awkward to ask.

Currently easy, and already served by the batch macros

Loss against epoch, residual distributions per layer, occupancy per half-stave. A UI should carry these, but they are not the reason to build one.

Currently awkward — the actual case for a platform

QuestionPanelSource
Which sensors moved, and by how much? Detector map, color-encoded by any of the six DoF, with a shared scale across layers weights.txt + geometry
What changed between step s and s + 1? Difference map on the same scale. This is the view that does not exist today in any form — comparing steps means diffing two 24 120-row text files by eye. two weights.txt
Is there a coherent weak mode left? γ against φ, T against z, per layer. A systematic trend in these is the signature the residual histograms hide by averaging. weights.txt + geometry
Which sensors have stalled? Gradient magnitude against epoch, ranked; sensors whose gradient collapsed early separated from those still moving CostGradient_*.txt
Which sensors are outliers? Ranked table with drill-down to that sensor's residual distribution and occupancy weights.txt + monitor tree
Is the charge asymmetry closing? The 20 φ-patch |DIFF| series across epochs and steps train_done.log
A concrete motivating observation

Reading the six alignment columns out of the committed weights.txt gives mean |T1| ≈ 760 µm, mean |T2| ≈ 909 µm, mean |T3| ≈ 558 µm and mean |γ| ≈ 2.3 mrad, with a maximum |T1| above 8 mm on at least one sensor.

I do not know which step this file came from or what it is referenced against, so I am not claiming anything is wrong. The point is narrower: a per-sensor value of that size is invisible in a 24 120-row text file and unmistakable on a map. That asymmetry — between how the data is stored and how the eye finds structure in it — is the whole argument for the first tier.

Section 05The real blocker

Everything that governs a run is a preprocessor define. nDATA and nEPOCH in YMLPParallel.h; TrackRejection, RANGE_CHI_IB/OB, Update_pTmin/max, DET_MAG, FITMODEL, MONITORONLYUPDATES_MODE and the monitoring switches in DetectorConstant.h. Changing any of them means recompiling.

For tiers 1 and 2 this is irrelevant — they read what a run produced. For tier 3 it is the dominant cost, and there are two ways through it.

  1. Generate the headers. The UI writes DetectorConstant.h and YMLPParallel.h from a form, then triggers the existing compile-and-run path. This is not a hack: run_profile_beam.C already generates YMLPBeamProfile.h exactly this way, so the pattern is established in the codebase and the build already recompiles per run through ROOT macro loading. Cheapest route, and it preserves the compile-time constant folding the numerics may depend on.
  2. Move configuration to runtime. Cleaner and enables parameter scans within a campaign, but it touches the hot path — several of these defines size fixed arrays and guard #ifdef blocks that compile whole monitoring subsystems in or out. MONITORHALFSTAVEUNIT and MONITORSENSORUNITprofile are structural, not just values. This is a real refactor of the module, not a wrapper.

Route 1 is the pragmatic choice and is what I would propose if tier 3 is ever wanted. It should not be attempted before tier 2 exists, because a launcher without monitoring is strictly worse than the current shell scripts.

Section 06Recommended path

Build tier 1 first, as a single self-contained page. The reasoning:

  • It needs no infrastructure, no deployment and no ALICE software environment, so it can be shared the same way the workflow document is.
  • It validates the data model — the sensor indexing, the geometry join, the DoF scaling — before any of that gets baked into a service.
  • It answers the step-difference question, which is the one genuinely missing capability rather than a nicer rendering of an existing plot.
  • If it turns out the map is not useful in practice, nothing has been spent on a backend.

Concretely, tier 1 needs one preparation step outside the browser: exporting the sensor geometry once. ReconstructGeometries already writes gSx, gSy, gSz per ChipID into XXXXGeom.root, so this is a single uproot read producing a static JSON of about 24 120 entries. After that the page is fed by weights.txt files alone.

Tier 2 becomes worthwhile once more than a few campaigns are being compared, since that is when manual bookkeeping of step directories starts to cost more than a service would. Tier 3 should wait for a demonstrated need to launch runs from outside a terminal.

Section 07Open questions

Points I could not settle from the repository alone, roughly in order of how much they affect a tier-1 design.

QuestionWhy it matters
Is the committed weights.txt the final deployed set, and what step is it from? Determines whether the parameter magnitudes noted in section 03 are expected, and sets the color scale for the map.
Are the six parameters absolute, or relative to ITSAlignment.root? Decides whether the map needs the O2 reference export at all, which is the only ROOT-environment dependency in tier 1.
Is a XXXXGeom.root available, or would ReconstructGeometries need to be run once? The one preparation step standing between the current state and a working map.
How many steps does a typical campaign run, and are the tarballs retained? Sets whether step history is a two-file comparison or a real time series, which changes the tier-2 data model.
Would this stay internal, or be shown alongside the workflow document externally? Affects whether the page should carry explanatory context or assume the reader runs the alignment.
